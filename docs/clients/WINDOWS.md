# Windows Client Alpha

The Tauri application bundles a dedicated React interface and native Rust transport. It does not open the server's website as its application window and does not require a local server installation. Connect it to a separately running Windows or Linux server using the same v1 API.

## Build and run on Windows

Install Node.js 24, stable Rust (MSVC toolchain), Visual Studio C++ Build Tools and WebView2. The .NET SDK and FFmpeg are needed only when running the server or integration fixtures on this computer.

```powershell
npm ci --prefix frontend
npm ci --prefix clients/windows
cd clients/windows
npm run tauri -- dev
# To package the native host and bundled UI:
npm run tauri -- build --bundles nsis,msi
```

The frontend dependency install is required because the Windows app reuses the existing web player and visual styles. The application opens a native window; enter the server origin, connect, sign in, browse/search and select a video. Initial server administration remains in the web UI. The server defaults to loopback: connecting from another computer requires deliberate, correctly secured server/reverse-proxy configuration and explicit AllowedHosts. Do not enable wildcard CORS to make this work.

Optional remembered sessions use **Windows Credential Manager**, keyed by the exact normalized server origin. Only the server address/theme are stored in a plain preferences JSON file. Passwords are transient and never saved. No certificate-verification bypass exists; remote HTTP, redirects and server addresses containing credentials are rejected. Certificate problems remain visible errors.

## Networking boundary

The locally bundled renderer has narrow Tauri capabilities. Rust owns session cookies, obtains CSRF tokens and allows only known v1 operations. API responses are size-bounded and requests have deadlines. Media URLs are generated by Rust, not accepted from a remote server response.

The video element uses a per-session random capability URL on `127.0.0.1` with an ephemeral port. The bridge accepts only media IDs, GET/HEAD and Range/If-Range, forwards cookies through the authenticated Rust client and streams data without buffering an entire movie. It never forwards cookies to the renderer, serves arbitrary server paths, listens on LAN interfaces or follows redirects. Stream responses are no-store and stop on local session cancellation. Capability URLs rotate on login, logout and server changes. The capability exists only in process memory; a compromised current OS user is outside this boundary. Do not log/copy these local capability URLs.

The production CSP permits IPC and loopback media, not arbitrary server scripts. No remote IPC capability is granted. Unexpected top-level remote navigation closes the window. Media is treated as untrusted data; the server cannot supply executable HTML to the player.

## Playback and desktop features

Direct Play uses the machine's WebView2 runtime. Runtime `canPlayType` observations are reported, but **EXE/MSI build success is not a codec test**. Real H.264/AAC, VP9/Opus, HEVC, AV1 and HDR behavior must be tested on representative Windows machines. Unsupported playback produces a visible error and sanitized report. Track metadata is displayed; selection stays disabled because the server cannot honor it yet. Movie/series identification remains server roadmap work.

Native video controls supply pause, seek, volume and fullscreen. When focus is outside a form/control, Space/K toggles playback, F requests fullscreen and the arrow keys seek ten seconds. Tauri high-DPI windowing is used, but physical DPI/device testing remains necessary. System/light/dark themes and remembered origins are provided. Native notifications, Windows media-session controls and signed automatic updates remain follow-up work, not implemented features. Updates are manual in this alpha.

### Native playback alternative

If WebView2 testing shows insufficient coverage, add a Rust `PlaybackEngine` interface with WebView2 and **libmpv** adapters. The native engine must receive authenticated headers in process (never command-line tokens), respect session cancellation and report position/track/error events through the same client contract. Evaluate native child-window/texture rendering, keyboard/focus, HDR surfaces, GPU selection and libmpv/codec redistribution licenses before bundling binaries. Keep the current API/progress transport unchanged. Do not silently fall back to untested third-party players.

### Updates and independent versions

Server 0.2.0-alpha.1, client 0.1.0-alpha.1 and API major 1 are separate versions. Windows CI emits the executable plus real NSIS EXE and WiX MSI installers as workflow artifacts. Files retain the builder's true filenames; the artifact label identifies client version and architecture. Installers are unsigned until maintainers supply Authenticode credentials. Installer signing and Tauri updater signatures are separate concerns: private keys belong in protected CI secrets, public updater keys/manifests in a reviewed future configuration. No automatic updater or stable publication is enabled.

## Tests

```powershell
npm test --prefix clients/windows
cargo test --locked --manifest-path clients/windows/native/Cargo.toml
dotnet build MediaServer.sln
python scripts/test-native-client.py
```

The native integration test generates a synthetic video and starts a fresh real backend. It verifies cookies/CSRF, protected ranges, remembered-session restore, progress conflicts and revocation without pretending an IPC mock is a real server. Windows CI additionally tests the Windows credential vault and compiles/packages the actual Tauri application. Physical Windows playback and installer interaction require manual testing; see VALIDATION.md.
