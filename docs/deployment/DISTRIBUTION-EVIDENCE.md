# Distribution evidence (#2)

The native server packaging job generates these files **before** archiving or
compiling installers, so Windows setup.exe, Linux DEB/tar and macOS PKG/tar contain
identical evidence for their respective source/runtime:

- `inventory/SBOM.spdx.json`: SPDX 2.3 package metadata and locked archive hashes.
- `inventory/THIRD-PARTY-INVENTORY.json`: declared dependency license metadata,
  evidence filenames, source commit, target runtime and coverage limitations.
- `inventory/license-evidence/`: bounded copies of available license and notice
  files; no dependency code is imported or executed by the generator.

NuGet metadata comes from the exact restored package graph and local nuspecs.
Self-contained Microsoft.NETCore.App and Microsoft.AspNetCore.App runtime packs
are additionally identified from the published `Api.runtimeconfig.json` and
`Api.deps.json`. Their versions, target runtime and restored package identities
must agree. Both Microsoft's license and upstream third-party notices are copied
into the evidence directory and included in the SPDX/report component list.
Missing terms, notices, frameworks or unexpected runtime packs fail packaging.
These runtime-pack components do not claim a lockfile archive checksum: their
provenance is the published application's manifests and restored nuspecs.
Browser metadata comes from the committed npm lock and installed production
packages; development-only npm packages are excluded. A missing/ambiguous NuGet
package or mismatched browser identity/version fails publication rather than
emitting invented evidence. Package metadata and license file sizes are bounded;
license paths must remain within restored package roots. Absolute cache paths do
not appear in the output. Start with an empty output directory; stale evidence
causes a failure and is never silently reused or deleted.

`licenseDeclared` and `licenseConcluded` intentionally remain `NOASSERTION` in
SPDX. Upstream declarations are preserved as **unreviewed metadata** in the report
and comments. This report is evidence for maintainers to review, not a statement
that redistribution obligations are fulfilled. Lock hashes identify downloaded
package archives; they do not assert that installed files are byte-identical to
the archive. The intentionally fixed epoch creation timestamp makes inventory
bytes repeatable for the same source, runtime and restored graph; the source
commit identifies the build, not that timestamp.

## Desktop Rust/Tauri inventory

Official desktop packaging generates a separate inventory for Windows x64, Linux
x64, Intel macOS and Apple Silicon macOS. `scripts/desktop-inventory.py` runs
`cargo metadata --locked --filter-platform <target>` against the Tauri manifest,
then follows normal and build dependency edges from the desktop application.
Dev-only and unrelated target packages are excluded. This graph can include build
tools and feature-unified dependencies; it is not a measurement of linked code.
Generating metadata does not execute dependency build scripts.

Every external component must match its name, version and exact source in
`Cargo.lock`. Registry entries retain the locked SHA256 archive checksum. Git
forks retain their full commit identity and distinct SPDX IDs/package URLs;
registry checksums are never invented for Git sources. First-party desktop/core
code remains covered by the project's existing bundled LICENSE and NOTICE.

The `inventory/` resource directory contains `SBOM.spdx.json`,
`THIRD-PARTY-INVENTORY.json`, `license-evidence/` and `SHA256SUMS`. The generator
copies bounded standard-named license/notice files, including nested notices and
explicit Cargo `license-file` paths. Git workspace notices can be read within the
checkout, never outside it. Missing notice files are flagged in the report even
when a declared license exists. A component with neither a declared license nor
a notice file fails inventory generation; malformed graphs, lock mismatches and
unsafe evidence paths also fail. Existing nonempty output is never reused.

The release-only Tauri configuration embeds these resources without changing
development builds. Generated evidence lives outside the cached Cargo target
directory, so cached builds cannot restore stale inventories. macOS DMG retries
reuse the already generated inventory.
Hosted checks compare every inventory file in the installed Linux DEB, copied
macOS app or administratively extracted Windows MSI with the generated bytes.
MSI extraction proves package contents, not a physical Windows installation.
The EXE/MSI share the same resource configuration; only the MSI has this extraction
check. CI also retains the inventory alongside the installers as a build artifact.
The normal release checksums cover the installers containing the evidence.

For a local release build, first run (from the repository root, with a clean
`artifacts/desktop-inventory` output):

```sh
python3 scripts/desktop-inventory.py --runtime linux-x64 --commit "$(git rev-parse HEAD)"
cd clients/windows
npm run tauri -- build --bundles deb --config src-tauri/tauri.release.conf.json -- --locked
```

Choose the matching runtime for the native build machine; generating another
target's graph does not cross-compile the application. These inventories retain
unreviewed license metadata and available evidence. They do not establish legal
compliance or replace review of notices and source obligations. Browser notices
remain bundled separately. OS libraries, WebViews/native SDKs, Rust's toolchain
runtime and Android dependencies are outside this inventory's coverage.

## Android runtime inventory

Each application debug/release variant generates its own `assets/inventory/`
before asset merging. The app bundle carries release evidence at
`base/assets/inventory/`. The generated assets contain `SBOM.spdx.json`,
`THIRD-PARTY-INVENTORY.json`, `SHA256SUMS` and `license-evidence/` with original
Maven POMs and available standard-named archive license/notice files. AAR notices
inside `classes.jar` are retained too. App instrumentation tests, JVM tests and
compiler/plugin classpaths are not inventoried as application runtime inputs.

Gradle exports the exact resolved runtime component identities, original external
artifacts and each component's resolved POM. First-party app/core code remains
covered by the bundled project license and notice. The generator records observed
SHA256 hashes of external AAR/JAR inputs in the report. These are hashes of this
build's downloaded artifacts, not lockfile archive checksums or assertions about
transformed DEX/native code. Application/core compile and runtime versions are
strictly pinned in their committed Gradle lockfiles (details below). Runtime graph
entries also include metadata-only platforms/BOMs and
annotations, so presence in the graph does not establish linked-code inclusion.

Only direct POM license declarations are interpreted; parent inheritance and
property expressions are not resolved. Original POM metadata is retained, with
missing direct license declarations and missing archive notice files flagged for
review. SPDX license conclusions remain `NOASSERTION`. No license URLs are fetched
or treated as vetted license text, and dependency code is never executed by the
Python generator. Missing POMs, inconsistent identities, unsafe XML/archive paths,
oversized evidence or malformed archives fail generation. Validated output is
published together; no partial inventory is available to asset merging.

Generation runs for each requested app variant even when compiled code is cached.
Only the task-owned generated asset/report directories are replaced. Review copies
live in `app/build/reports/dependencyInventory/debug` and `release`. Python 3.11+
is required for Android builds; use `-PinventoryPython=python` when appropriate on
Windows. This graph/POM export task does not support Gradle configuration caching.

CI compares the entire embedded inventory in the actual debug APK, unsigned release
APK and unsigned release AAB with fresh generated evidence, including source commit,
version and variant. Missing, duplicate, additional or changed files fail the gate.
The separate `android-inventory` artifact preserves review copies without changing
the existing APK artifact layout used by emulator tests. The unified release job
downloads both artifacts and repeats verification before packaging. Normal release
checksums cover the APK/AAB files that contain the inventories.

This inventory does not cover the Android OS, SDK/toolchain, build plugins or
separately supplied native binaries. It does not change signing behavior or certify
license compliance. Missing declarations/notices and any source
redistribution obligations still need maintainer review.

### Android version locks

`clients/android/dependency-locks.gradle.kts` activates Gradle's strict dependency
locking for registered `*CompileClasspath` and `*RuntimeClasspath` configurations
in the app/core modules. This covers app debug/release inputs and registered unit
and instrumentation test classpaths. Missing lock state, additions/removals that
do not match it and incompatible required versions fail resolution. A newer
transitive version alone does not silently replace a locked version. Both
`app/gradle.lockfile` and `core/gradle.lockfile` must be committed.

CI resolves all these classpaths before building, without write/update flags, and
checks that the two tracked lockfiles remain unchanged. A separate integration
test applies the actual policy to a temporary project and local Maven repository:
it publishes a newer transitive version, verifies ordinary resolution stays
pinned, exercises an explicit targeted update, then verifies missing lock state
and an unreviewed dependency addition fail without writing production lockfiles.

Use the app/core `resolveDependencyLocks` tasks for read-only checks. Updating
requires an explicit `--write-locks` or `--update-locks group:artifact`; see the
Android README. Regeneration resolves every registered locked classpath, including
variants not compiled by that command, without ambiguously selecting first-party
Android AAR artifacts. The resolution task does not support configuration caching.

Locking controls selected module versions, not mutable bytes at the same Maven
coordinates. Gradle plugin/buildscript/compiler configurations, Android SDK inputs,
artifact signature/checksum verification and whole-build reproducibility are not
covered by these classpath locks. Inventory archive hashes remain observed evidence,
not verification against a trusted checksum policy.

  or notices flagged by the Android and desktop Rust/Tauri inventories.
- Review every redistributed license, notice and corresponding-source obligation.
- Retain the container's exact installed package list, FFmpeg license/build output
  and corresponding-source bundle; these already have a separate release path.
- Perform clean physical-machine install and rollback checks; hosted installer
  tests are automated runner evidence, not personal-device certification.
- Establish artifact signing. Checksums detect corruption, not publisher identity.

The existing base-image digest pins, locked dependency restores, unsigned-alpha
labels, actual installer smoke tests and rollback guidance remain in place.
The whole build is not claimed bit-for-bit reproducible: runner images, apt inputs,
platform toolchains and packaging timestamps can still vary.
